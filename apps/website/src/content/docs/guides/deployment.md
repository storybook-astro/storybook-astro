`storybook build` behaves differently depending on [`renderMode`](/reference/configuration/#rendermode). Static mode produces plain static files; server mode produces a static UI plus a small Node render server that must be hosted alongside it. This guide covers both.

## Static mode (any static host)

With the default `renderMode: 'static'`, `storybook build` emits a single `storybook-static/` directory of plain HTML, CSS, and JS. There's no server involved at runtime, so it deploys to any static host exactly like any other Storybook build: Cloudflare Pages, Netlify, GitHub Pages, S3 + CloudFront, or a plain web server serving the directory.

```bash
storybook build
# deploy storybook-static/ to your static host of choice
```

The tradeoff is that Astro component stories are pre-rendered with their default args, so the Controls panel is disabled for them (framework component stories are unaffected). See [Static Builds](/how-it-works/static-builds/) for how that pre-rendering works, and [Server Builds](/how-it-works/server-builds/) if you need interactive Controls in production.

## Server mode

With `renderMode: 'server'`, `storybook build` emits `storybook-static/` (the Storybook UI, same as above) plus a sibling `storybook-server/` directory containing a standalone Node render server (`index.js`, a [Hono](https://hono.dev/) app) and a `project/` snapshot of every Astro story component your build reaches. The Storybook UI calls this server on demand to keep Controls interactive for Astro components. Because it needs a real filesystem and Node APIs, it requires a Node-capable host — see the [platform support matrix](#platform-support) below before choosing a target.

### On Vercel

Vercel (Node serverless functions) is the maintained, tested path for server mode. `integration/astro6-server` in this repo is a complete working example — the steps below mirror it.

#### 1. `vercel.json`

```json
{
  "$schema": "https://openapi.vercel.sh/vercel.json",
  "framework": null,
  "buildCommand": "cd ../.. && yarn build:packages && cd - && yarn build",
  "outputDirectory": "storybook-static",
  "functions": {
    "api/storybook-astro/[...path].js": {
      "includeFiles": "storybook-server/**",
      "maxDuration": 60,
      "memory": 1769
    }
  }
}
```

`"framework": null` is critical. Without it, Vercel's Astro framework auto-detection takes over the build and ignores your `api/` directory entirely — the render function never gets deployed, and requests to it 404. `includeFiles: "storybook-server/**"` ships the `storybook-server/` output (the render server and its component snapshot) into the function's bundle; `maxDuration: 60` and `memory: 1769` give cold starts (Vite SSR + Astro Container boot) enough time and headroom.

#### 2. The API route handler

Vercel's Node runtime needs a file at `api/storybook-astro/[...path].js` that adapts the Hono app to Vercel's function signature, using [`hono/vercel`](https://hono.dev/docs/getting-started/vercel):

```javascript
// api/storybook-astro/[...path].js
import app from '../../storybook-server/index.js';
import { handle } from 'hono/vercel';
// Generated by ../../scripts/generate-vercel-trace-hints.mjs during `yarn build`;
// ships the packages the render server resolves through Vite at runtime.
import './_vercel-trace-hints.js';

const renderServer = handle(app);

// Method exports (not a default export) make Vercel's Node runtime invoke
// this with the web-standard signature — `request` is a fetch Request with an
// absolute URL, which `handle(app)` from hono/vercel expects.
function handler(request) {
  const url = new URL(request.url);

  url.pathname = url.pathname.replace(/^\/api\/storybook-astro/, '') || '/';

  return renderServer(new Request(url, request));
}

export const GET = handler;
export const POST = handler;
export const OPTIONS = handler;
```

Point `framework.options.server.serverUrl` at this route in `.storybook/main.js` (`'/api/storybook-astro'`), so requests stay same-origin with the static UI.

#### 3. The trace-hints build step

Vercel's file tracer only bundles files reachable from static imports, and its `includeFiles` option silently ignores anything under `node_modules`. The render server, though, boots a Vite SSR server that resolves packages like `astro` and framework integrations dynamically at request time — files the tracer can't see statically. `scripts/generate-vercel-trace-hints.mjs` closes that gap by generating `api/storybook-astro/_vercel-trace-hints.js`, a never-executed module containing literal `import()` calls for every runtime file those packages need, forcing the tracer to bundle them completely. Run it after `storybook build`:

```json
{
  "scripts": {
    "build": "storybook build && node ../../scripts/generate-vercel-trace-hints.mjs"
  }
}
```

Skipping this step produces `Failed to resolve entry for package …` errors in production once you deploy.

#### 4. Vercel dashboard settings

- **Framework Preset**: irrelevant at runtime since `vercel.json` sets `"framework": null`, but make sure the dashboard preset isn't overriding it — set it to "Other" if in doubt.
- **Monorepos**: set **Root Directory** to the integration app's directory (e.g. `integration/my-app`), and enable **"Include source files outside of the Root Directory in the Build"** — the build command `cd`s up to the workspace root to run `yarn build:packages` first, and Vercel needs permission to read outside the Root Directory to do that.
- **Environment Variables**: if you set `authToken`/`STORYBOOK_ASTRO_SERVER_TOKEN` (see below), add it as a project environment variable available at build time — it's compiled into the server bundle during `storybook build`, not read at request time.

#### 5. Auth (optional)

Server mode supports an optional bearer token, enforced with a timing-safe comparison on the server:

```javascript
// .storybook/main.js
export default {
  framework: {
    name: '@storybook-astro/framework',
    options: {
      renderMode: 'server',
      server: {
        serverUrl: process.env.STORYBOOK_ASTRO_SERVER_URL ?? '/api/storybook-astro',
        authToken: process.env.STORYBOOK_ASTRO_SERVER_TOKEN,
        authHeader: process.env.STORYBOOK_ASTRO_SERVER_AUTH_HEADER, // defaults to 'authorization'
      },
    },
  },
};
```

Set `STORYBOOK_ASTRO_SERVER_TOKEN` (and optionally `STORYBOOK_ASTRO_SERVER_AUTH_HEADER`) in your hosting environment before running `storybook build` — the token is baked into the server bundle at build time, so it must be present during the build, not just at runtime.

### On any Node.js server or container

Outside Vercel — Docker, Fly.io, Railway, Render, a plain VPS, anything that runs a long-lived Node process — mount the generated Hono app directly with [`@hono/node-server`](https://hono.dev/docs/getting-started/nodejs) alongside a static file server for `storybook-static/`:

```javascript
// preview-storybook.mjs
import { resolve } from 'node:path';
import { pathToFileURL } from 'node:url';
import { Hono } from 'hono';
import { serve } from '@hono/node-server';
import { serveStatic } from '@hono/node-server/serve-static';

const port = 6017;
const builtStorybookServer = (await import(pathToFileURL(resolve('storybook-server/index.js')).href)).default;

const app = new Hono();

app.route('/api/storybook-astro', builtStorybookServer);
app.use('/*', serveStatic({ root: './storybook-static' }));
app.get('*', serveStatic({ root: './storybook-static', path: './index.html' }));

serve({ fetch: app.fetch, port }, () => {
  console.warn(`Storybook preview ready at http://127.0.0.1:${port}`);
});
```

Run it with `node preview-storybook.mjs` after `storybook build`. This is exactly the pattern used to serve the built artifacts locally for the `integration/astro6-server` and `integration/astro7-server` example apps (their `yarn serve` script), and it generalizes to any container image or process manager — build the image with your build command, then run this script as the container's entrypoint.

### Netlify Functions

Expected to work via [`hono/netlify`](https://hono.dev/docs/getting-started/netlify) with the same shape as the Vercel adapter (swap `hono/vercel`'s `handle()` for Netlify's, and Netlify's function bundler for the trace-hints step). This is **untested** — there's no maintained example in this repo yet. If you try it, please report back.

### Cloudflare Workers / Pages Functions

**Not supported, and not fixable by configuration.** The render server boots a Vite SSR dev server and reads the component snapshot from a real filesystem at `storybook-server/project/`; Cloudflare Workers have no Node `fs` module and no child processes. This isn't a missing adapter — it's a fundamental mismatch between what server mode needs and what the Workers runtime provides.

The one plausible route on Cloudflare is [Cloudflare Containers](https://developers.cloudflare.com/containers/), since it runs a real Node process in a container — the generic "any Node.js server" pattern above would apply. There's no maintained example of this in the repo.

### Pure static hosts and other edge runtimes

By design, unsupported — use `renderMode: 'static'` instead. Static mode has no server-side runtime requirements at all.

## Platform support

| Platform | Server mode support |
|---|---|
| Vercel (Node serverless functions) | ✅ Works — maintained example (`integration/astro6-server`, `integration/astro7-server`) |
| Node.js server/container (Docker, Fly.io, Railway, Render, a VPS) | ✅ Works — mount with `@hono/node-server` |
| Netlify Functions | ⚠️ Expected to work via `hono/netlify`, untested |
| Cloudflare Workers / Pages Functions | ❌ Not supported — no Node `fs`/child processes |
| Cloudflare Containers | ⚠️ Should work (Node-in-container), no maintained example |
| Pure static hosts / edge runtimes | ❌ Not applicable — use `renderMode: 'static'` |

## Latency expectations

Each process running the render server boots a Vite SSR dev server and an Astro Container the first time it handles a request:

- **Cold start**: roughly 10–15 seconds on Vercel, since a fresh serverless function instance has to boot the SSR server before it can render anything.
- **Warm renders**: roughly 0.3–0.5 seconds once the process is warm and the SSR server is already running.

The Storybook client's render request for server mode uses a 60-second timeout specifically to tolerate cold starts — a render that would otherwise fail while a fresh instance boots gets the time it needs instead of erroring out.
